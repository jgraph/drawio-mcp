# MCP App Server

Renders draw.io diagrams inline in AI chat interfaces using the MCP Apps protocol.

## Key Files

| File | Purpose |
|------|---------|
| `src/shared.js` | Shared logic: `buildHtml()`, `processAppBundle()`, `createServer()` |
| `src/index.js` | Node.js entry (Express + stdio transports) |
| `src/worker.js` | Cloudflare Workers entry (Web Standard fetch handler) |
| `src/build-html.js` | Build script: generates `generated-html.js` for the Worker |
| `server.json` | MCP Community Registry manifest (`io.draw/mcp`, remote `https://mcp.draw.io/mcp`) — publish runbook in README "Publishing to the MCP Registry"; keep `version` in lockstep with `package.json` |
| `snippet/mcp_edge.js` | Cloudflare Snippet in front of the Worker on `mcp.draw.io`: answers pings, notifications, session-less requests, GET/HEAD/DELETE/OPTIONS and OAuth discovery probes without a Worker invocation — see [Edge snippet](#edge-snippet) |
| `openai-plugin/` | OpenAI Plugins Directory package (`.codex-plugin/plugin.json`: names, descriptions, starter prompts, policy URLs, icon; `.mcp.json`: the server, which can never change on an existing plugin) — zipped and uploaded as a new version in the portal; its own `version`, runbook in `OPENAI-SUBMISSION.md` |

## Architecture

### How the HTML is built

At startup (Node.js) or build time (Workers), the HTML is assembled. The draw.io **viewer**, **drawio-elk**, and **drawio-mermaid** load from the `viewer.diagrams.net` CDN via `<script src>` — they're large, cached cross-session by the browser, and stay version-synced with each draw.io release (same host + release cadence as the viewer). The remaining bundles are inlined so the sandboxed iframe needs no further fetches for them:

- **`app-with-deps.js`** (~319 KB, from `node_modules/@modelcontextprotocol/ext-apps`) — MCP Apps SDK browser bundle. The bundle is ESM (ends with `export { ... as App }`), so `processAppBundle()` strips the export statement and creates a local `var App = <minifiedName>` alias. This makes it safe to inline in a plain `<script>` tag inside the sandboxed iframe.
- **`pako_deflate.min.js`** (~28 KB, from `node_modules/pako`) — for compressing XML into the `#create=` URL format.
- **libavoid** (the obstacle-avoiding orthogonal edge router behind `routing: "libavoid"`) is **not vendored/inlined** — the HTML loads the pure-JS router bundle (`libavoid.min.js`, a self-contained classic script that publishes `globalThis.Avoid` and parks `window.__libavoidReady` synchronously — no WASM, no fetch, no `wasm-unsafe-eval` needed) + shared routing core from the `viewer.diagrams.net` CDN (`js/libavoid-js/`), like drawio-elk and drawio-mermaid. Requires the draw.io release that ships the pure-JS two-file layout there. The routing math is `AvoidRouting.computeRoutes` from `libavoid-routing.js` — the canonical `drawio-dev js/libavoid-js/` artifact, byte-identical to what the draw.io editor bundles and the mcp-tool-server vendors. `buildHtml` accepts `options.libavoidJs` to inline a local build instead (dev). See `vendor/libavoid/README.md`. `routeWithLibavoid` passes each vertex's style transform (`libavoidShapeFrame` → `AvoidRouting.shapeFrame`: rotation, direction, flips) and each pin's `exitPerimeter`/`entryPerimeter`, so rotated shapes are routed as drawn; against a CDN core from before rotation support (no `shapeFrame`) it routes them unrotated, as before. A floating edge end gets one candidate pin at the middle of each side (`LIBAVOID_SIDE_MIDPOINTS`) instead of the shape's centre, and the pass asks the core to nudge apart the segments attached to a shape (`opts.nudgeShapeSegments`): from the centre, every edge leaving a shape shared its first segment and their labels piled up. Of those midpoints, a floating end only gets the sides that face the other end (`libavoidFacingPins`), as draw.io's orthogonal edge style draws them: shapes stacked vertically connect bottom to top, shapes side by side connect side to side, a diagonal pair gets both facing sides. Alone, libavoid takes the route with the fewest bends, which entered a shape below from its side, so a load balancer's edges to two servers under it left its bottom and turned into the servers' sides. When another shape blocks the corridor between the two ends (a loop back along a flowchart column), all four sides stay allowed; shapes drawn around an end (a container, a background band) don't block. A row of a table (an ER column, a class attribute: a child of a `stackLayout`/`tableLayout`/`table` container) only gets its left and right side (`libavoidRowPins`), since its top and bottom border the rows next to it; with all sides, relations entered tables through their header. The pass reroutes only right-angle edges (`libavoidRoutesEdge`: `orthogonalEdgeStyle`, `elbowEdgeStyle`, `entityRelationEdgeStyle` and the other segment styles, not `curved=1`). Straight and curved lines are a choice the diagram type makes (use case links, network cables, state transitions, mind maps) that orthogonal routes would undo, so they stay as drawn. XML without `postLayout` or `routing` is routed anyway when a right-angle edge, as the built-in router draws it, runs through a shape it doesn't connect, through a label outside a shape or through a lane's title band (`edgesCrossShapes`, checked at finalize, `opts.autoRoute`): the model can't see where the basic router draws its lines. Containers and shapes drawn around an end don't count, as in the routing core's `filterEnclosing`. A vertex with `labelPerimeter=1` and a label outside the shape also passes that label (`libavoidOutsideLabel`, from the viewer's `getLabelPerimeterSide`), so the core routes around it and ends edges on that side at its far edge, where draw.io ends them. Both need the draw.io release after 32.5.5: an older CDN core ignores the option and the label (the midpoint pins then share their first segment like the centre did), and an older viewer has no `getLabelPerimeterSide`. `LIBAVOID_PATH` (a directory with `libavoid.min.js` and `libavoid-routing.js`, e.g. drawio-dev's `src/main/webapp/js/libavoid-js`) inlines a local build in the Node server for testing before that release, next to `VIEWER_PATH`.

Loaded from the CDN (not inlined):

- **`viewer-static.min.js`** — the draw.io viewer (`GraphViewer`, `Graph`, `mxCodec`, `mxUtils`, …).
- **`drawio-mermaid.min.js`** (`/js/mermaid/`) — native Mermaid parser + layout that emits draw.io cells via `mxMermaidToDrawio.parseText(text, config)`. Replaces the upstream ~2.7 MB `mermaid.min.js` + `extensions.min.js` runtime. Supports 28 diagram types. Reads `globalThis.ELK` on init. Built from `jgraph/drawio-mermaid`.
- **`drawio-elk.min.js`** (`/js/elk/`) — Eclipse Layout Kernel + the mxGraph ↔ ELK bridge, self-publishing IIFE. Defines `var ELK` (engine) plus `ElkLayout` / `ElkAdapter` / `ElkApplier` as globals, consumed by drawio-mermaid and the `postLayout` pass. `ElkLayout` is the single source for the layout pipeline (`prepare`/`execute`), the per-algorithm `DEFAULTS`, the `MENU_PRESETS` (layout name → algorithm + direction) and the `CANONICAL_EDGE` treatment (`edgeStyleMode` + `corners`) — shared verbatim with drawio-dev's editor. The MCP's `applyPostLayout` drives it via `new ElkLayout(...).prepare(...)`. Built from `jgraph/drawio-elk`.

Script load order is `viewer → pako → elk → mermaid`, preserved because all are classic (non-async) `<script>` tags and execute in document order — external CDN tags block parsing just like inline ones. drawio-elk defines `var ELK` + `ElkLayout` and must come before drawio-mermaid (mermaid reads `globalThis.ELK` on init and throws otherwise); mermaid must come after the viewer so its `mermaidShapes.js` side-effect sees `mxCellRenderer`/`mxActor`. The viewer code reaches `ElkLayout` straight off the (CDN-loaded) bundle for the `postLayout` pass — no separate shim script.

**Shape sizes in the ELK pass.** `applyPostLayout` runs ELK with `resizeParent: false`, so it keeps every shape's size; only containers are refit. The layered pass takes the unconnected top-level cells out of the flow and stacks them above it (`ElkLayout.placeIsolatedTopLevelAbove`). Up to the bundle on the CDN in 32.6.10 it also narrowed each of them to the flow's width, a rule meant for the Mermaid title. With a single connected pair, every other box took that pair's width: in a Claude.ai test with one Sensor → Hub edge, all eight unconnected boxes rendered 80 wide (sent 100 to 140), and their labels stopped fitting. drawio-elk now narrows only text cells whose label doesn't wrap, since those draw the same at any width (`test/verify-bridge-isolated.mjs` there). Until a draw.io release ships that bundle, `applyPostLayout` saves the width of every top-level shape without children before ELK applies and restores any it changed, centred where ELK put it (`saveLeafWidths` / `restoreLeafWidths`). Text cells that don't wrap are left to the narrowing, as in the fixed bridge. Once the CDN has the fix the stopgap changes nothing and can go.

For local dev, set `VIEWER_PATH` / `ELK_PATH` / `MERMAID_PATH` to a built bundle to inline it instead of hitting the CDN (e.g. testing a drawio-elk/mermaid build before it's published). `processElkBundle` / `processMermaidBundle` accept both the published IIFE form and an ESM build. The published CDN files self-publish their globals (no `export{}`), so those functions are no-ops on them.

### Sandbox constraints

- The MCP Apps sandbox uses `sandbox="allow-scripts"` but **not** `allow-same-origin` — Blob URL module imports fail silently. That's why we strip the ESM export and use a plain `var` alias.
- Links open through the host (`openUrl`), never `<a target="_blank">` — no `allow-popups`. `app.openLink({ url })` (`ui/open-link`) everywhere but ChatGPT, where `window.openai.openExternal({ href, redirectUrl: false })` opens them: ChatGPT's link check for `ui/open-link` prints the whole URL, and for a `#create` link it was taller than the window, which cut off its buttons. `openExternal` trusts the targets in `_meta["openai/widgetCSP"].redirect_domains` of the app resource (`REDIRECT_DOMAINS`: app.diagrams.net, www.drawio.com; `ui.csp` can't carry them, so that key repeats the rest of the CSP too), and `redirectUrl: false` keeps ChatGPT from appending `?redirectUrl=…`, which would land in the `#create` hash. ChatGPT reads these settings from its copy of the app resource's metadata, made when the plugin was scanned, but loads the HTML live, so a metadata change only reaches it after a **Rescan** in the portal (`OPENAI-SUBMISSION.md`). Until the rescan of 2026-10-31 its copy predated `redirect_domains`, and every link still got the check. `test/open-link.test.js` checks both paths.
- ChatGPT's fullscreen header has its own "Open in draw.io" button. Without a target it opens the component's iframe path on `ui.domain`, our Claude sandbox domain, so it answered "Not Found" (2026-10-30). `commitDiagramXml` passes every new `drawioEditUrl` to `window.openai.setOpenInAppUrl({ href })`, so it opens the diagram. ChatGPT accepts that target only from the CSP's connect domains or the widget domain, not the redirect domains (`openInApp.validateUrl` in its bundle), so `CONNECT_DOMAINS` lists app.diagrams.net although the viewer fetches nothing from there. ChatGPT checks it against the app's current metadata, so it works in chats from before the change too, but a ChatGPT tab opened before the Rescan keeps the old metadata until it reloads (the first test after 1.4.6 failed for that reason).
- `GraphViewer.processElements()` requires nonzero `offsetWidth` on the container — hence `min-width: 200px` on `#diagram-container`.

### Node.js vs Workers

| | Node.js (`src/index.js`) | Worker (`src/worker.js`) |
|---|---|---|
| **Transport** | `StreamableHTTPServerTransport` (Express) | `WebStandardStreamableHTTPServerTransport` |
| **HTML build** | Reads bundles from `node_modules` + `vendor/` at startup | Pre-built via `build-html.js` → `generated-html.js` |
| **Session management** | None — a server per request; the session's one bit of state rides in its id, the resource flag sits in an in-memory Map | None — a server per request; the session's one bit of state rides in its id |

### Cloudflare Workers Architecture

The Worker serves `/mcp` **statelessly**: every request gets its own `createServer()` + `WebStandardStreamableHTTPServerTransport`, built in the Worker and dropped with the response. Nothing is held between requests, so it scales out with the Workers runtime and there is no Durable Object on the request path.

- **Sessions (2025-era protocol):** an `initialize` is answered with a minted `Mcp-Session-Id`, `ui-<uuid>` or `noui-<uuid>` — whether the client declared the `io.modelcontextprotocol/ui` capability, the one piece of per-session state the server needs (see [Clients without an MCP Apps UI](#clients-without-an-mcp-apps-ui)). A later request's server reads it back from the header (`uiSession` option of `createServer`), and its transport is marked initialized (`_initialized`) since it never saw the handshake. Any session id is accepted — there is no "session not found" anymore; an id without either prefix (issued before this scheme) reads as "not declared".
- **Session-less requests** other than `initialize` get the transport's own `400 Server not initialized` — the answer MCP 2026-07-28 clients (claude-code, copilot-cli, some Claude.ai traffic) get for their `server/discover` probe before falling back to `initialize`.
- **`GET /mcp` → 405** (no standalone SSE stream: the server never sends anything outside a response), **`DELETE` → 200** (nothing to release).
- **`MCPSessionManager`** is now one Durable Object per session id (`idFromName(sessionId)`, RPC methods `markUiResourceRead` / `uiResourceRead`), holding only the "fetched the app resource" flag in storage, dropped by an alarm 24 h after the last fetch. Only clients that did *not* declare the UI capability ever reach it — on `resources/read` of the app and on `create_diagram` — so it sees a tiny fraction of the traffic. A failed lookup counts as "not read", which only appends the fallback link. The class name is kept from the old design to avoid a wrangler migration.
- **`/health`** is the uptime probe (Pingdom watches `https://mcp.draw.io/health`): it runs an `initialize` through the same per-request path as `/mcp` and answers `200 ok` (`503` otherwise). It exists because monitors count the non-2xx of a session-less `GET /mcp` as down. The Node server answers `/health` directly.

**Why stateless?** Until 2026-09-30 every session's server + transport lived in the memory of sharded Durable Objects (4, then 16, routed by the session id's first hex char). A DO handles its requests one at a time and has 128 MB: with each session building its own shape-search tag map (~8 MB), the shards hit their memory limit ~1,200 times an hour and reset (dropping every session), and on 2026-09-30 they overloaded outright ("Durable Object is overloaded"). Claude.ai opens a new session per connector refresh (`initialize` → `tools/list` → `resources/list`, rarely a call, never a `DELETE`), so the DOs mostly held idle sessions — ~0.3 MB each once they had served `tools/list`. The DOs were also the dominant cost (billed per active object, 128 MB each). The only state a session needs is one bit, which fits in its id.

**MCP 2026-07-28** drops sessions and `initialize` altogether (capabilities arrive per request in `_meta`). Supporting it natively means SDK v2 (`@modelcontextprotocol/server` + `ext-apps` 2.x); v2's default handling of 2025-era clients is stateless too but loses their `initialize` capabilities, so the capability-in-session-id scheme stays for them.

### Edge snippet

`snippet/mcp_edge.js` is a [Cloudflare Snippet](https://developers.cloudflare.com/rules/snippets/) (snippet `mcp_edge`, zone `draw.io`, Enterprise). Snippets run before Workers and cost nothing per request, so the requests whose reply never depends on the server are answered there and never invoke the Worker:

- a `ping` (200, the `id` echoed, `mcp-session-id` echoed) and a `notifications/*` message (202), both within a session
- any JSON-RPC message but `initialize` without a session (400 "Server not initialized")
- `GET` (405), `HEAD` (405), `DELETE` (200, or 400 without a session) and `OPTIONS` (204) on `/mcp`
- OAuth/OIDC discovery probes (`/.well-known/oauth-*`, `/.well-known/openid-configuration`, `/mcp/.well-known/…`: 404)

Everything else is passed on with `fetch(request)` and reaches the Worker unchanged. That includes `initialize`, `tools/*` and `resources/*`, batches, bodies over 1 KB or of unknown length, a Content-Type whose media type isn't `application/json` (the SDK parses it, so `text/plain; a=application/json` gets its 415), SSE-only clients, unknown `mcp-protocol-version`s and any message the SDK's strict JSON-RPC schemas might reject (ids and progress tokens must be safe integers). Every reply the snippet makes carries `x-drawio-mcp-edge: snippet`.

**Why:** Copilot CLI pings each open session every 21 s, forever, so windows left open keep pinging. In October 2026 that was ~71% of all Worker requests. Worker requests had grown from 2.3M a day (2026-09-29) to 7.1M a day (2026-10-12), and an 88 s `wrangler tail` sample put ~85% of them in the categories above.

**Keeping it exact:** the snippet must answer exactly as the Worker would. `test/edge-snippet.test.js` holds the Worker's recorded replies, checks the pass-through cases, and fails when the SDK's `SUPPORTED_PROTOCOL_VERSIONS` no longer matches the snippet's copy. `EDGE_COMPARE_URL=<worker origin> npm test` also compares every answered case live. Run it against staging after an SDK update or a change to `worker.js`'s trivial paths (CORS headers, GET/DELETE handling), and redeploy the snippet when they change.

**Rule:**

```
http.host eq "mcp.draw.io" and (http.request.uri.path eq "/mcp" or starts_with(http.request.uri.path, "/.well-known/oauth-") or starts_with(http.request.uri.path, "/.well-known/openid-configuration") or starts_with(http.request.uri.path, "/mcp/.well-known/"))
```

**The zone's snippet rules belong to drawio-dev.** `src/main/server/cf/cf-snippets/rules/draw.io.json` there is the `draw.io` zone's complete rule list, and every draw.io production deploy (`cf-deploy.yml`) replaces the zone's rules with it. It lists this rule since drawio-dev `970f312abc`; before that, the 32.5.1 deploy (2026-10-13 14:47 UTC) deleted it and the Worker took all the traffic again until it was restored at 16:32. So change the rule in that file as well as on the zone. The code is not in drawio-dev (no `cf-snippets/mcp_edge/`, so its deploy skips it): deploy it from here, `cf snippets update mcp_edge --zone <zone id> --file snippet/mcp_edge.js --metadata '{"main_module":"mcp_edge.js"}'`. Updating rules on the zone by hand (`PUT /zones/{zone}/snippets/snippet_rules`, which **replaces all rules in the zone**): GET them first and send them all back.

**Rollout:** deploy with ` and any(http.request.headers["x-drawio-mcp-edge-test"][*] eq "1")` appended to the rule, so only requests carrying that header reach the snippet. Check them against production (the `x-drawio-mcp-edge` header shows which side answered), then drop the condition. **Rollback:** disable or remove the rule, which takes effect at once. Snippets have no logs: watch the Worker's daily requests in `workersInvocationsAdaptive` (GraphQL) drop instead.

**DOMAIN secret:**
- Set via `wrangler secret put DOMAIN`
- Value format: `{hash}.claudemcpcontent.com` where hash is SHA-256 of the endpoint URL (first 32 hex chars)
- Current value: SHA-256 of `https://mcp.draw.io/mcp`, truncated to 32 hex chars + `.claudemcpcontent.com`
- Used in `resources/read` response `_meta.ui.domain` for Claude.ai iframe sandbox origin

**wrangler.toml migrations:**
- The v3 migration tag is already applied in production
- Do NOT add a new `[[migrations]]` tag unless the DO class name changes — it will cause deploy conflicts

## Clients without an MCP Apps UI

`create_diagram` appends a second text block carrying an `app.diagrams.net/?pv=0&grid=0` URL (or to a self-hosted editor, see **Self-hosted editor** under [Viewer toolbar](#viewer-toolbar)) (`#R` with the XML, like "Open in draw.io" below; `#create=` with the source for Mermaid, which draw.io converts) when the connected client doesn't render the app — a plain MCP client (Codex CLI, a terminal agent, a script) otherwise receives the JSON payload and nothing renders the diagram anywhere. Detection is `capabilitiesDeclareUi()` (the `io.modelcontextprotocol/ui` capability from `getUiCapability`, carrying `RESOURCE_MIME_TYPE`) OR `uiResourceRead`, a per-session flag set when the client actually fetches the `ui://` resource — which covers a host that renders through its own negotiation without declaring the capability.

The declaration is trusted except from the clients in `UI_DECLARED_NOT_RENDERED` (`clientUiState()` → `"hidden"`, by the `clientInfo` of `initialize`): those declare the capability and never render the app. The one entry is `codex-mcp-client` version `0.0.0`, OpenAI's hosted Codex harness. ChatGPT's Work mode runs a plugin's own MCP server through it whenever the prompt mentions the plugin (`plugin://drawio@openai-curated-remote`, which the starter prompts on the plugin page insert), and the page shows those calls as a "Made N tool calls" line, never the app: users got neither the diagram nor the link (2026-10-31, reproduced with `wrangler tail`: user agent `codex-mcp-client/0.0.0`, OpenAI's network, one `ui-` session). A typed `@draw` inserts an app mention (`app://asdk_app_…`) instead, which ChatGPT calls through the connector (user agent `openai-mcp/1.0.0 (Codex)`) and renders. The Codex app and CLI send their release version and keep their declaration; within one version some sessions declare the capability and some don't.

Where the two signals live depends on how long the server instance lives. The stdio server has one instance for the whole session, so both sit on the instance. Both HTTP entries build one per request and pass `createServer` a `uiSession`: `declared` and `hidden` come from the session id minted at `initialize` (`ui-` / `hidden-` / `noui-`, from `clientUiState`), and the resource flag from that session's `MCPSessionManager` Durable Object (Worker — see [Cloudflare Workers Architecture](#cloudflare-workers-architecture)) or an in-memory Map with the same 24 h expiry (Node). The Node HTTP transport stays stateless: `src/index.js` sends the minted id in `Mcp-Session-Id` itself and reads it back from the header. Until 2026-10-13 it minted none, so every Node and Docker client got the link, VS Code (which declares the capability) included.

The block is only ever *appended*: the app reads the FIRST text block (`content.find`), so a host that renders but wasn't detected keeps working. For most clients the server only knows that they didn't declare the capability, and some of those do show the diagram (Claude.ai often declares nothing up front), so the note stays a condition ("if this client doesn't show the diagram inline"). Worded as a fact in 1.4.5 ("assume the user can't see this one"), Claude showed the diagram and told the user it didn't display. For a `"hidden"` client the server knows the user sees nothing, and there the condition was ignored: the model in ChatGPT Work assumed the diagram showed and left the link out. So that note says the user can't see the diagram and first asks the model to call another draw.io `create_diagram` tool that shows diagrams in the conversation, the draw.io app in ChatGPT, with the same arguments, giving the link only otherwise: ChatGPT Work offers the server both as the plugin's MCP server (never renders) and as the app (renders), and a model can't copy a link of several KB reliably (its copy in Work broke off after 447 characters and didn't open). Short links are not an option: they would store the diagram, which the service promises not to do. XML goes into the URL as-is, so a requested `postLayout` adds a note saying the link opens the authored coordinates (that pass lives in the app). Mermaid goes in as `type: "mermaid"` and the editor converts + lays it out on open — and a requested `postLayout: "elk"` *does* survive, because it is selected in the source: `withElkLayout` from `shared/mermaid-elk.js` (the canonical copy; the browser-side `withElkRenderer` in the app HTML is the same transform, kept in sync by hand since the self-contained HTML can't import).

## A short reply after the diagram

`create_diagram` ends every result, XML and Mermaid, with a note (`appendAnswerNote`): the user sees the diagram itself, so the model shouldn't describe or list what it shows, and once it is done drawing it replies in at most two sentences unless the user asked for an explanation, for example with what it assumed or changed, or the offer of a next step `shared/chat-view-xml.md` asks for. Without the note the model summarized the diagram the user was already looking at.

- **Where the client renders the app** (`clientUiState` "renders", or it fetched the resource), the note says the user already sees the diagram in the chat. Elsewhere it is a condition like the link note ("inline or through the link"), and the reply is short besides the link: the server doesn't know whether Claude.ai shows the diagram.
- **For a hidden client** (`clientUiState` "hidden") the link note just before it says the user can't see the diagram, so this note says nothing about what the user sees and doesn't make the link optional ("the user will look at it themselves", "besides the link"): the conditional wording read as the last block told the model the user sees the diagram and that the link is optional, the slip the hidden link note exists to prevent.
- **It is the last block**, after the swap note, the warnings and the link, so the model reads it last; the viewer reads the first text block, the payload, and never sees it.
- **Within the hosts' rules:** plain text about the result the tool just produced, under 320 characters, no markup, nothing about other tools, and the user's request comes first ("unless the user asked for an explanation"). Result text only: `tools/list` doesn't change, so the ChatGPT app needs no rescan. `test/answer-note.test.js` covers the wording per client, the order of the blocks and the length.
- **Measured** in November 2026 with `claude -p` (Sonnet 5.5, Opus 5.5) on an ER diagram, a swimlane flowchart (both XML) and an OAuth sequence diagram (Mermaid), the old and the new server side by side, timed from the `create_diagram` call to the end of the answer. With the server told the client renders the app, as for ChatGPT, Claude.ai, VS Code and Cursor: Sonnet's answer went from a median of 408 to 115 output tokens (1,165 to 347 characters) and ended 4.4 s after the diagram instead of 5.7 s (9 runs each); Opus's from 605 to 97 tokens, 1.9 s instead of 6.2 s (5 runs each). Without a UI (Claude Code itself, so the link is appended), the text besides the link shrank from about 1,330 to 390 characters, but the time is the link's: an answer with the 1–3 KB link ran to 900–2,400 tokens, and the models gave it in 6 of 8 answers instead of 4 of 8, so the answer didn't end sooner (Sonnet 9.8 s instead of 11.5 s, Opus 30 and 55 s instead of 6 and 31 s).

## Model normalization

Before that, `repairDiagramXml` (`shared/repair-xml.js`, shared with the tool server) fixes the mechanical slips LLMs make in the XML string: text around the diagram (a leaked tool-call tag after it, `…</mxGraphModel></xml>`), `<` or a stray `&` in attribute values, and the default layer written as its own parent. When the leaked text carries a `postLayout`, `direction` or `routing` argument with a value `XML_OPTION_VALUES` accepts (the same arrays the `create_diagram` schema uses) and the real argument is missing, `leakedArguments` recovers it. A well-formed diagram passes byte-identical. In LLM tests of the tool server these slips caused every broken diagram, 15 of 473; see `mcp-tool-server/AGENTS.md`.

Right after the repair, `expandDiagramShorthand` (`shared/diagram-shorthand.js`) expands the two shorthands `shared/chat-view-xml.md` teaches, so the model writes less: in the November 2026 benchmark the time to a diagram was almost all the model writing XML, styles were about half of it, and 75 of the 86 cells of a class diagram were attribute rows. A vertex with `rows="PK id|FK book_id|…"` becomes a list table (a `swimlane` with `childLayout=stackLayout` under its own style, height from the rows, a width for the longest row when none is given) followed by one `text` row cell per entry, 26 px tall (font size + 10 above 16), `---` an 8 px separator line; a row's id is `table.name`, the name being the first word after key markers (`PK`, `FK`, `UK`) and UML visibility, numbered when repeated, its position when there is none, and an edge naming a row by position (`loan.2`) or in another case is pointed at it. `role=step|decision|start|end|error|data|external|container` in a vertex style becomes the calm theme's shape, colors, `fontSize=14`, `html=1` and `whiteSpace=wrap`, keys written beside it winning in place (a shape of its own replaces the role's), a container inside another one white, and a vertex without width or height the grid size of its role; on a table a role only sets the colors. String in, string out: no `rows` attribute or known `role` key is left, a diagram without them passes byte-identical, and expanding twice changes nothing. Start tags are scanned with their quoted values taken whole, since XML allows a raw `>` in a value and the repair escapes only `<` (`value="Retries > 3?"`, a row `List<Item>`): at the first `>`, such a cell lost its `vertex`, `rows` and `style` and stayed unexpanded. The viewer inlines the same code (`createDiagramShorthand.toString()`, self-contained for that reason) and runs it on the healed partial XML and in `finalizeStreamingView`, since it draws from the raw tool input before the result arrives. On the partial XML (`{ partial: true }`) a table cut off before its `<mxGeometry>` stays as written: `streamInsertCell` hides a vertex without a geometry until one arrives, and the made-up geometry a complete table without one gets would show it at the top left first. The tool server, the skill and the project instructions don't expand them, so the shared references don't mention them. `test/diagram-shorthand.test.js`.

After the shorthand, `getIconResolver().applyToXml` (`shared/icon-resolver.js`, shared with the tool server) replaces `icon=<provider> <service>` in a vertex style with the style of the official icon from `shared/icon-table.js`: the current AWS, Azure, Google Cloud and Kubernetes sets, generated from the shape index by `shape-search/generate-icon-table.js`. The icon's keys win over the cell's (a theme's `fillColor` would repaint an AWS tile), the label keys stay, and a cell with children on its page or `container=1` only takes an AWS group (`icon=aws vpc`); one larger than 100 × 100 without children takes a group when one fits as well as an icon (a VPC drawn before its subnets), and a service icon otherwise. A label color of the library that is hard to read on the cell's page (`isHardToRead`: a gray under 4.5:1 against the page's `background`, white without one, or any color under 3:1) becomes the calm theme's text color `#1B1F24` (`LABEL_COLOR`), as the role styles and the references write it, while a `fontColor` of the cell still wins. On a white page that is the 128 Google Cloud products (`gcp2`, `#999999`, which a benchmark judge marked down as hard to read), AWS's VPC group (`#AAB7B8`) and its generic subnet (`#879196`); AWS's dark labels (`#232F3E`), the colored labels of its other groups, which match their borders (`#D86613` and the like), and Google Cloud's current icons (`#000000`) stay; Azure and Kubernetes icons write no label color. On a dark page (the dark theme's `background="#0F172A"`, which `applyToXml` reads from each `mxGraphModel`) the grays stay, as they read well there, and a label that doesn't, such as AWS's `#232F3E`, gets the dark theme's text color `#F1F5F9` (`DARK_PAGE_LABEL_COLOR`): a cell the model wrote without the theme's `fontColor` would otherwise get a dark label on a dark page. Cisco has no icons by name. The resolver is one per process for every caller, so its cache keeps only the last 500 names, and a name longer than 100 characters matches nothing without being searched. A name that matches nothing stays as written and `unresolvedIconWarnings` tells the model what to write. The viewer inlines the resolver and the table (`expandIcons`, ~150 KB, ~35 KB gzipped) and applies it to the partial and the final tool input after `expandDiagramShorthand`, as the server does, so icons show while the XML streams in; the `gcp2` icons, data URIs of 200 KB together, stay on the server and show as a gray placeholder, with the label color the result will have on that page, until the result. In the AWS architecture case of a November 2026 benchmark (Claude Code, `claude -p`), Sonnet wrote the names in 5 of 6 runs instead of making 9 `search_shapes` calls: the diagram was done after 39 s instead of 55 and had 7.1k instead of 10.3k characters. `test/icon-names.test.js` covers the server and the viewer; the resolver's cases are in the tool server's `test/icon-resolver.test.js`.

Every XML diagram passes through `normalizeDiagram` (`shared/normalize-model.js`) right after `normalizeDiagramXml` and the repair, before the payload reaches the app. It repairs three things generated XML carries: edges parked on the layer although both terminals sit inside one container (they render, but ELK reads an edge's coordinates in the frame of the node containing it, so the connector escapes the container — [#64](https://github.com/jgraph/drawio-mcp/issues/64)), edges written without a geometry (not rendered at all), and containers that would clip a child (grown, never shrunk).

Doing it here rather than inside the layout keeps `postLayout` free of hierarchy side effects, and the corrected diagram is what the viewer renders, what "Open in draw.io" exports, and what the fallback URL carries. The implementation is `MxGraph.normalizeModel` in `shared/mx-model.js` — a port of drawio-dev's `Graph.normalizeModel`, i.e. the desktop CLI's `--normalize` — driven over the XML by `shared/mx-xml.js`; idempotent, and it rewrites nothing else.

Right after the normalization, `snapWaypoints` (`shared/edge-waypoints.js`, shared with the tool server) moves the first or last waypoint of an edge onto the line of its fixed connection point when it lies less than 3 px (`SNAP_DISTANCE`) off it: on a left or right side its y, on a top or bottom side its x. An edge with `exitX`/`entryX` leaves the shape at a right angle, and draw.io's orthogonal router runs the line from there to the waypoint; a waypoint written at y = 510 for a connection point at y = 508.8 gets a 1.2 px jog next to the shape, and an arrowhead there takes its direction from that piece and points along the side. In the hand-written disk overview that led to it, the Time Machine arrow pointed up the side of its target; snapped, its last segment is 35 px. The pass only snaps where draw.io keeps the connection point where the style puts it: rectangular outlines, or the middle of a side of any outline (draw.io projects other points of a round or slanted one onto it), not rotated, flipped or turned shapes, nor corners. It rewrites only those edges and is idempotent. `test/edge-waypoints.test.js` runs it through `create_diagram`; the cases are in the tool server's test of the same name.

After it, `addLabelPerimeters` (`shared/label-perimeter.js`) adds `labelPerimeter=1` to vertices with a label outside the shape, centered on one side (`verticalLabelPosition` top or bottom, or `labelPosition` left or right), unless their style already has the key: draw.io ends edges on that side at the label's far edge, the convention of cloud architecture diagrams. The editor sets the key the same way on new shapes; existing diagrams don't have it. Then `fitEdgeLabels` (same module) gives all edges, labeled or not (as new edges in draw.io after 32.5.5 have it), and the labeled label cells of edges the label gap (`labelBackgroundColor=default;defaultLabelBackgroundColor=page`, _Transparent_ in the _Background_ list of draw.io's Text tab: draw.io after 32.5.5 cuts the label out of the line instead of painting a white box; 32.0.2 to 32.5.5 paint the page color, older viewers the white box), unless a background is set, and puts the label of a straight horizontal edge just above the line (`verticalAlign=bottom`) where it fits between the shapes, and `labelPlacement=auto` on every labeled edge (draw.io after 32.5.5 picks above or on the line by the segment under the label, also for bent edges; older viewers ignore it). Both rewrite only those cells and are idempotent.

## The diagram as shown, for the model

The model only has the arguments it sent, but the viewer can show something else: Mermaid converted to draw.io XML, an ELK layout or libavoid routing pass, the user's layout toggle. Every change to what is shown goes through `commitDiagramXml`, which schedules `sendModelContext` (500 ms, so a render and its layout pass coalesce; the layout and routing state is taken with the XML, since a render's first commit comes before the layout state is set). `modelContextText` writes what the diagram is and how to change it (start from this XML, pass it as `xml` without `postLayout` / `routing` so the positions stay; for Mermaid, simple changes can stay in the Mermaid source), followed by the flat XML as shown — for Mermaid the converted cells, not the `wrapGroup` wrapper "Open in draw.io" uses.

- **When:** plain XML shown as sent isn't repeated. Mermaid and any pass are sent, and once a diagram has been sent, every later change is (so the toggle back to "as authored" updates the model too). Above `MODEL_CONTEXT_MAX_CHARS` (60,000) nothing is sent.
- **How:** `app.updateModelContext` (`ui/update-model-context`) when the host declares the `updateModelContext` capability. The host keeps only the last update and passes it on with the user's next message. Otherwise, in ChatGPT, `window.openai.setWidgetState({ modelContent })`. `[model-context]` console lines say which channel was used, or that there was none.
- **Nothing reaches draw.io:** the XML, the image and the layout check go from the iframe to the host's conversation, so the privacy page doesn't change.
- `test/model-context.test.js` runs `modelContextText` from the template source.

### What the rendering shows (#92)

The XML doesn't tell the model how wide a label comes out, where draw.io routes a line or what ends up on top of what: those exist only once the viewer has drawn the diagram. So the update carries two more things, measured on the graph as shown (after layout and routing):

- **The layout check** (`layoutCheck`, for every host that takes model context): a short list of labels wider or taller than their shape, labelled shapes on each other, labels on labels (from 4 px) or on labelled shapes, and one line per connector with everything found on it, with ids and sizes in diagram units, at most 20 lines. On a connector it finds the shapes it runs through or the labels of shapes or lanes (`edgesCrossShapes`) and, from `edgeLayoutIssues`: an arrowhead without room (its last straight piece shorter than half the arrowhead, so it points along the side or over the bend), a step of 1 to 3 units in the line (from 1 on rounded lines, where the two corners make an S, from 1.5 on square ones), a run of 20 or more along a frame's border (within 4) or in a gap under 30 between two frames side by side, more than 10 on top of another edge where one hides the other (another color, width or dash) or both join the same two shapes (lines of one look meeting on their way are a bus, a merge or the trunk of a tree, also when their arrowheads differ), and its label on a frame's border, on another edge's line, or turned (`horizontal=0`). Frames are shapes with a rectangular outline drawn around smaller shapes: containers, zones, subnets. One line per edge, because the chip counts the lines: the hand-written diagram the edge rules came from got 28 lines for its 4 defects without the grouping, and 6 with it. A list asks the model to fix the problems when it next changes the diagram, and to offer once when the next request is about something else: without that line nothing makes the model act on it, and without "once" an unrelated question would turn into a round of fixes. It leaves out what overlaps by design: unlabelled shapes (walls, chart cells, backgrounds), labels inside a frame at least 16 times their size, labels outside a shape or turned, shapes under 8 px, lifelines below their head, and lines that aren't connected at both ends, are sequence messages, are curved, or join two unlabelled anchors (sankey, git graph); a shape that holds a labelled shape (a card whose name is in a box of its own) counts as labelled (`layoutCheckAnchor`). Round and diamond shapes are tested by the box inside them. The crossings come from `edgesCrossShapes(graph, found)`: with `found` it collects every crossing over the connectors `layoutCheckedConnector` accepts; without it, it still decides the automatic routing pass exactly as before. The rules were tuned on ~600 diagrams from the benchmark and gallery runs, replayed through the server's passes: 532 came out clean, and the ones sampled from the rest (a title crossed by a line, a multiplicity on an attribute, rack labels piled up, sequence labels running into the number badges of the Mermaid conversion) were real defects. The edge rules were tuned on 598 diagrams in November 2026 (the 67 gallery diagrams, 239 Mermaid conversions, 286 draw.io templates and examples, and 6 cases of the hand-written diagram: the original, the versions Sonnet and Opus made through the app server, a flowchart and an org chart), replayed the same way: 26 got edge findings, none of the Mermaid conversions, the Opus version, the flowchart or the org chart among them. Of the 58 edges they flagged, a visual review found 5 doubtful, all in hand-made templates (two arrowheads that read fine, two lines between dashed frames, two wires on top of each other); the labels on borders and lines, the steps and the runs along borders were all real. The overlap rule at first also compared arrowheads and flagged buses and tree trunks, so it compares color, width and dash only. A host that takes text only gets the check before the XML; for XML shown as sent, alone and only when it found something.
- **A PNG of the diagram** (`renderModelContextImage`), only when the host declares `hostCapabilities.updateModelContext.image` and isn't ChatGPT, which shows each context block as an attachment in its message box (not tried with an image yet). draw.io's own client-side export (`Editor.prototype.exportToCanvas`, in the viewer bundle) runs on an `Object.create(Editor.prototype)` with the graph, at most 1568 px on the long side and twice the diagram's size, in the scheme the diagram is painted in (a `light-dark()` probe, not `prefers-color-scheme`; a scheme change sends the image again). Remote images are loaded with CORS and inlined (the icon service and the viewer's own images allow it); one that can't be is left out instead of tainting the canvas, and nothing goes through draw.io's image proxy. An SVG image can't use the page's web fonts, so every family without a generic one gets `Helvetica, Arial, sans-serif` (Recursive came out in Times). The image is sent on every render, also for XML shown as sent; the XML still only when it differs.

The update waits for `document.fonts.ready` (at most 2 s), since a web font still loading would make the labels measure the wrong width. Hosts pass it on with the user's next message, so the model sees it on its next turn, not within the turn that drew the diagram. The Claude desktop app's Code tab declares images and passes them on (seen with `read_widget_context`); it loads the app HTML once per session, so a new build only shows in a new session. `[model-image]` and `[layout-check]` console lines show the size, time and count. `test/layout-check.test.js` runs the check on a stand-in graph, and the content and fallback helpers, from the template source.

### Asking for a fix in one click

By the time the update reaches the model, the turn that drew the diagram is over. So when the layout check finds something, the toolbar shows a chip, "Fix N issues" (`#fix-layout-btn`, with an amber warning icon; its tooltip says "N layout issues"). A click sends the host a user message, "Fix the layout issues the draw.io viewer found in this diagram." (`ui/message` through `app.sendMessage`; in ChatGPT `window.openai.sendFollowUpMessage`). The host starts a model turn, and the image and the check are already in the model's context. The click first waits for the update in flight (`modelContextInFlight`), so the message never overtakes the check.

- **Only on a click:** a message sent on its own would start a turn the user didn't ask for, under their name, and after each fix the next check would send another.
- **Only with something to fix:** `updateFixLayoutChip` shows the chip when the check counted at least one issue and the host declares `hostCapabilities.message` (or has `sendFollowUpMessage`). With nothing found, "Fix" would be the wrong word, so there is no chip.
- **It counts what is on screen:** every commit hides the chip until the check of the new state (`scheduleModelContext`), and the layout toggle hides it at once (`applyLayoutChange`). The toggle exists for XML with `postLayout: "elk"` and for every Mermaid flowchart, and the two layouts usually have different issues. After a sent message the chip stays hidden for that layout (`fixLayoutAskedFor`, by layout state): a toggle offers it for the other layout, but not again for the one already asked about. A host that rejects the message gets "Could not send" for 2 s, then the chip again.
- **Hosts:** Claude.ai declares `ui/message`: in a test on 2026-11-06 the click posted the message and Claude fixed the diagram. For the other hosts, the `[model-context] host` console line logs `message` and `followUp`; `[fix-layout]` lines show the chip and the send.
- The message is in English, whatever the language of the chat.

## Inline height and the readable top view

Inline, the iframe grows to the diagram's natural height up to `inlineHeightCap()`: 800 px, at most 90 % of `screen.availHeight` (the screen, because the iframe's own height follows our `sendSizeChanged` and would feed back), never below 480 px. `--inline-max-h` on the root carries the same value to the CSS. Hosts resize the iframe both ways on `sendSizeChanged`, Claude.ai included. Expand switches the cap to 1000 px; fullscreen fills the window.

Where fitting a tall diagram whole would shrink it below `STREAM_READABLE_MIN_SCALE` (0.75, so 12 px labels stay 9 px), the camera settles on its top at that scale instead: `computeDefaultViewTransform`, used after drawing, layout passes, the layout toggle and Expand, and by `streamFollowNewCells` once there is nothing left to follow, so the window resize that follows the host's size change keeps the top view instead of zooming back out to fit-whole. The card's bottom edge fades while the diagram continues below (`.more-below`, from `updateMoreBelowCue`), and the Fit button and double-click still show the whole diagram. A diagram limited by its width keeps fit-whole. Before this, a fixed 480 px cap shrank tall flowcharts and sequence diagrams until their labels were unreadable: the 2026-10-16 benchmark spike scored draw.io's readability below Excalidraw's for exactly that. `[inline-height]` console lines show the cap, the host's reported height and when the top view is used.

## Viewer toolbar

**Labels.** "Open in draw.io", "Copy" and the layout-issues chip carry text labels; the other buttons are 30 px icons. A label never wraps (`white-space: nowrap`, an ellipsis if it is ever squeezed). Whenever the labels can't be shown whole, `fitToolbarLabels` first drops the chip's label (`chip-compact`, the amber icon stays), then puts the toolbar in `compact` mode, icons only and every button square. A label squeezed to nothing counts as cut: its `offsetWidth` is 0, so the test asks whether its button is shown instead. With every button shown, all labels fit from about 660 px, and "Open in draw.io" and "Copy" keep theirs down to about 575 px. The chip first said "Fix N layout issues", which needed about 720 px: in Claude.ai's inline frame that made the whole toolbar `compact` and took the "Open in draw.io" label with it. It re-measures with the labels shown when the toolbar's width changes (`ResizeObserver`), when a button is shown or hidden, and when a label changes ("Copied!", the chip's count) (`MutationObserver`). The icon buttons never shrink (`flex-shrink: 0`), so the labels are what gives way, and in `compact` mode no button shrinks. In `compact` mode the gaps narrow to 4 px, which makes up for the split buttons' arrows.

**Narrow frames.** With every button shown (zoom, Open, Copy, Download, fullscreen, Expand, layout, the chip and help), the icons alone need about 420 px, and mobile chats are 350–390 px wide. There the `compact` toolbar wraps to a second row instead of cutting off the last buttons, as it did below about 385 px before the chip. `flex-wrap: wrap` applies only in `compact`, and `fitToolbarLabels` measures without it, so the labels go before anything wraps. When the wrap changes the toolbar's height, `fitToolbarLabels` calls `resizeContainerToFit`, which makes room for the second row where the frame's height is fixed (fullscreen).

**Download and Copy are split buttons.** A click on the button does what it always did (the `.drawio` file through `ui/download-file`; the XML to the clipboard). The 16 px arrow beside it opens a menu that starts with that same action, in bold and set off by a line as the default, followed by the image formats: Download .drawio, Download PNG and Download SVG (all through `ui/download-file`), and Copy as XML, Copy as Image and Copy as SVG (`navigator.clipboard.write` with a `ClipboardItem`, created in the click because the clipboard needs the user's gesture, its contents handed over as promises while they render). The wording follows draw.io's (its Edit menu has Copy, Copy as Image and Copy as SVG; `toolbarMenuEntries`). Copy as SVG writes what draw.io's does, an `<img>` with the SVG as a data URI as `text/html`, plus `image/svg+xml` only where `ClipboardItem.supports` says the browser writes it (Chrome from 124), since a `ClipboardItem` with a type the browser doesn't write fails as a whole, and the markup as `text/plain` for editors (`svgClipboardTexts`). Tested in a sandboxed frame like the hosts' (November 2026): Chrome 157 wrote all three types, Firefox 159 the HTML and the text; Safari takes Firefox's path (it writes no SVG type) and is untested. The arrow shows only when there is an image format, since a menu with the default alone would repeat the button. Until 1.8.0 the menus listed only the image formats. What a host doesn't support is hidden, never greyed out, and follows what it declares, never its name (`toolbarMenuFormats`, checked by `test/download.test.js`): the Download button and its menu need `hostCapabilities.downloadFile`; Copy as Image and Copy as SVG need the host to grant `hostCapabilities.sandbox.permissions.clipboardWrite` (the resource asks for it in `_meta.ui.permissions`) and a browser with `ClipboardItem` whose permission policy allows `clipboard-write`; PNG (Download and Copy) needs a canvas the viewer bundle's own check (`Editor.useCanvasForExport`, an SVG with HTML labels drawn to a canvas) found untainted. The images come from draw.io's own export code in the viewer bundle: `Graph.getSvg` and `Editor.exportToCanvas` on an Editor made with `Object.create(Editor.prototype)`, since its constructor would change the shown graph (chromeless, math rendering). Both carry the `.drawio` file (the SVG in its `content` attribute, the PNG in a `tEXt` chunk), so draw.io opens them for editing. The PNG is drawn at 2x in the theme the viewer shows; the SVG follows light or dark mode wherever it is shown. Both take the page color, shadow and `adaptiveColors` from the diagram's `mxGraphModel` (`diagramPage`, kept in `currentPage` by `applyDiagramBackground`), since the viewer's graph merges only the cells and has none of them: without that, a dark or blueprint theme lost its page and its light text landed on white or nothing. A diagram with `adaptiveColors="none"` is exported in its light colors (`exportTheme`), and its SVG gets a white page when it has none (`svgExportBackground`), as draw.io does. Images are embedded through `exportImageConverter`, which leaves absolute URLs as they are: draw.io's own converter would send every image not on the sandbox's origin through `viewer.diagrams.net/proxy`, which the sandbox can't reach, and leave the proxy URL in the SVG. Library SVGs (`app.diagrams.net/img/lib/…`, `icons.diagrams.net`) can't be fetched as text (not in `connectDomains`), so they are embedded as PNG at `Editor.svgRasterScale`.

**"Open in draw.io"** opens `#create={"type":"xml","compressed":true,"data":…,"effect":"pop"}`: the XML the viewer shows (for a Mermaid diagram, the converted XML wrapped by `wrapGroup` with its source in mermaidData), with the "pop" animation as draw.io creates the diagram. The plain links have no animation: the fallback link for clients without an MCP Apps UI and the tool server's links open XML as a raw `#R` link, and use `#create=` only for Mermaid (and the tool server's CSV), which draw.io converts in the browser because nothing has converted it to XML there. `?pv=0&grid=0` apply to both (draw.io reads them for every loaded diagram). `test/links.test.js` checks both forms.

**Self-hosted editor.** `DRAWIO_BASE_URL` points "Open in draw.io" and the fallback link at another draw.io, as in the tool server ([#91](https://github.com/jgraph/drawio-mcp/issues/91)). `editorLinkBase` builds the link up to its hash: the base URL with `pv=0&grid=0` added to its query (after a query of its own), any hash dropped; anything but an http(s) URL throws, so the Node server fails at startup. `buildHtml` puts it in the iframe as `window.__DRAWIO_EDITOR_URL`, which `generateDrawioEditUrl` reads; `createServer` builds the fallback link from it and adds its origin to the connect and redirect domains (`withEditorOrigin`), next to app.diagrams.net. Only the links move: the viewer, shape images and libraries still load from diagrams.net (`window.DRAWIO_BASE_URL`, the viewer's own base for those, stays app.diagrams.net), so the inline preview needs no sign-in to a draw.io behind SSO. The Node server reads it at startup. The Worker's HTML is built before the deploy, so `build-html.js` reads it from the deploying shell and exports it from `generated-html.js` as `drawioBaseUrl` for `createServer`, which keeps both links on one value; a `[vars]` binding would come too late for the HTML. `test/links.test.js` covers both links, the CSP and the validation.

**The "All changes will be lost!" dialog** (draw.io up to 32.4.5): after a `#create`, draw.io rewrites the hash with the diagram it created, and its `hashchange` handler compares the result with the hash from before the load. If they differ, it loads the link again and asks. They differ whenever the link isn't exactly what draw.io writes back: a Mermaid or CSV link, another deflate or JSON encoder, or a host that re-encodes the link on the way to the browser. VS Code does the last: a link opened as a URI goes out as `encodeURI(uri.toString(true))`, which leaves `:` `,` `+` `/` `=` unescaped. draw.io never rewrites a `#R` hash, which is why the button used `#R` from 2026-10-12 until the fix: drawio-dev `5170e37146` and `6ee7e71444` (2026-10-13, first release after 32.4.5) have `executeCreateObject` store the hash it rewrites to on the created file, and the `hashchange` handler doesn't load that hash again. Tested with every link format here, it removes the dialog; comparing decoded hashes only covers re-encoded XML links, and `history.replaceState` alone covers none, because `fileLoaded` has already cleared the hash. Deploy the button's `#create` only once app.diagrams.net runs that release, or VS Code users get the dialog again.

## MCP Apps SDK Patterns

- `registerAppTool` `inputSchema` uses Zod shapes (`{ key: z.string() }`), not JSON Schema objects
- CSP config goes on the **resource contents** `_meta.ui.csp`, not on the tool's `_meta.ui`
- `resourceDomains` includes `https://fonts.googleapis.com` and `https://fonts.gstatic.com` so Google fonts of `fontSource` styles load in the viewer (the font CSS is linked, it loads the font files) — e.g. the Recursive font of Mermaid 12 diagrams (`redux-color` theme)
- `_meta.ui.permissions` asks for `clipboardWrite` (Copy as Image, Copy as SVG), next to `csp` on the resource contents; the host says in `hostCapabilities.sandbox.permissions` whether it granted it
- TypeScript narrowing: use `if (block.type === "text")` before accessing `.text` on content blocks
- To accept more than a schema advertises, wrap it in `z.preprocess` (`lenient` in `src/shared.js`): the JSON schema in `tools/list` stays byte-identical to the wrapped one, so a tool can get more forgiving without a new tool definition (which the OpenAI and Claude directory listings were reviewed against). Put `.optional()` inside the wrapper: outside, it lets only `undefined` through and `null` fails before it is mapped. The SDK (1.32) answers a value the schema rejects with an `isError` tool result ("Input validation error"), which the Claude directory counts as a tool error
- The viewer renders from the raw tool input (`ontoolinputpartial`, `ontoolinput`) before the result arrives, so input the server corrects has to be read the same way there: `normalizeOptionValue` is inlined for the options, `diagramXmlStart` skips text before the XML, `expandDiagramShorthand` expands table rows and roles, `expandIcons` then resolves icon names, and a diagram under the other parameter is left to the result

## XML and Mermaid References

The `get_drawio_reference` tool (`{ format: "xml" | "mermaid" }`) returns one of two canonical reference files in `shared/`, with this server's chat-view sections inserted before their first section (`src/references.js`, `readReference`): `shared/chat-view-xml.md` (designing for the inline frame, one layout pattern per diagram type for XML the model places itself, changing a diagram, choosing a look) and `shared/chat-view-mermaid.md`. `readReference` also leaves out the shared sections a diagram in the chat doesn't use (`OMITTED_SECTIONS`: layers, tags, metadata and placeholders, cross-functional grids). That keeps the XML reference under 50,000 characters: Claude Code, and the hosts built on it, save a longer tool result to a file and show the model a 2 KB preview, so the model would draw without the reference (seen in tests on 2026-10-18 at 54.6 KB). `test/references.test.js` caps it at 48,000 and checks that the omitted headings still exist. Only `create_diagram` shows diagrams in the chat frame, and only its format rule has the model place flowcharts, class, state and other diagrams as XML; the tool server, the skill and the project instructions use the shared references without these sections.

- **`shared/xml-reference.md`** — loaded as the `xmlReference` option on `createServer()`; covers draw.io XML styles, the layout grid, edge routing, containers, metadata.
- **`shared/mermaid-reference.md`** — loaded as the `mermaidReference` option; covers syntax for all 28 supported Mermaid diagram types plus flowchart styling (`style`, `classDef`, `linkStyle`).

The `create_diagram` description stays short (~1.8k characters): the Mermaid-vs-XML decision with every Mermaid header keyword, the XML essentials, and an instruction to call `get_drawio_reference` once per format before the first diagram. Through app server 1.0.6 it carried both references (~55k characters), which broke VS Code Copilot's tool search: Copilot embeds tool descriptions in batches, and one description over the embedding limit fails the whole batch, other servers' tools included ([#76](https://github.com/jgraph/drawio-mcp/issues/76)). `test/tools.test.js` (`npm test`) caps every tool description at 2048 characters and checks that the tool returns both files. Guidance that only matters once a format is chosen belongs in the references, not in the description.

For the Cloudflare Worker, both files are pre-built into `generated-html.js` (exported as named strings) by `build-html.js` and re-imported by `worker.js`. The Node.js path reads them directly from `shared/` at startup.

## Mermaid Conversion

`convertMermaidToXml()` in `shared.js` is a thin synchronous wrapper around `mxMermaidToDrawio.parseText(text, null, {version: MERMAID_DEFAULTS_VERSION})` exposed by the inlined drawio-mermaid bundle. `MERMAID_DEFAULTS_VERSION` ("12", top of `shared.js`) is also passed by the streaming preview, stored by `wrapGroup` in the mermaidData behind "Open in draw.io" and added to `#create=` links of type `mermaid`, so the preview, the opened diagram and draw.io's re-conversion on edit all use Mermaid 12's defaults (no theme is forced; draw.io adapts the light themes to dark hosts). Version 12 diagrams of the redux themes use the Recursive Google font, which the viewer loads from Google Fonts (both hosts are in the CSP `resourceDomains`, see [MCP Apps SDK Patterns](#mcp-apps-sdk-patterns)). No listener plumbing, no 10 s timeout, no upstream mermaid runtime — `parseText` runs the full parse + layout pipeline and returns draw.io XML directly. The only wait before calling it is `waitForGraphViewer()`, because the cell factory still needs `Graph`, `mxCodec`, and `mxUtils` from `viewer-static.min.js`.

Returns `null` for unsupported diagram types — the wrapper converts that to a rejected promise so the UI surfaces a clear error.

## Shape Search Index

The `search_shapes` tool uses a pre-built index from `shape-search/search-index.json` (~10,000 shapes). The index is embedded in `generated-html.js` at build time (adds ~4 MB to the Worker bundle). The local search runs in-process; the tag lookup map (~100 ms to build, several MB) is built once per process or Worker isolate, on the first search, and shared by every server (`getTagMap`). If the index file is missing, `search_shapes` is silently not registered.

When the local index has no strong match for a query (no result exact-matched every term), results are supplemented live from the draw.io icon service (`icons.diagrams.net` — brand logos and general-purpose concept icons, returned as `shape=image` styles). The merge pipeline is `searchShapesAndIcons` in `shared/icon-search.js`: strong local results lead and icons only fill spare slots; weak (Soundex/OR-fallback) local results keep at most half the budget. A full page of strong local results makes no network request; a service failure degrades to local-only results. The endpoint is configurable via `createServer`'s `iconServiceUrl` option, wired to `DRAWIO_ICON_SERVICE_URL` in both entries (set to `off` to disable). `https://icons.diagrams.net` is whitelisted in the iframe CSP `resourceDomains` so the referenced icon images render in the inline viewer.

## Coding Conventions

## Accept Header / JSON Mode

Claude.ai sends `Accept: application/json, text/event-stream` (both). The server prefers JSON when both are present:

```js
const wantsSSE = acceptsSSE && !acceptsJson; // JSON wins when both present
```

- **JSON mode** (Claude.ai): the Worker's per-request transport is created with `enableJsonResponse: true`
- **SSE mode** (Claude Desktop): standard SSE streaming via `handleRequest()`
- This was a critical fix — the original code matched on `text/event-stream` alone, routing Claude.ai to SSE mode which it can't consume

## Debug Logging (`wrangler tail`)

Debug logging is **off by default**. Enable via `wrangler secret put DEBUG` (set to `"true"`). The worker includes diagnostic logging for debugging MCP protocol issues:

| Tag | Content |
|-----|---------|
| `[rpc]` | HTTP method, JSON-RPC method name, session ID (prefix + first chars), `NEW` for an `initialize` |
| `[transport-error]` | SDK-internal errors (e.g. "Server not initialized") |
| `[response]` | Method, session, mode (SSE/JSON), HTTP status, elapsed ms |
| `[response-body]` | Full response for `resources/list`, `resources/read`, `tools/list`, `tools/call` |
| `[ui-flag]` | A failed read/write of a session's "fetched the app resource" Durable Object |

Unexpected exceptions are always logged (`[error]`, with the stack) and answered with a JSON-RPC `500`.

**Note:** At high traffic, `wrangler tail` enters sampling mode and drops messages. Use `wrangler tail --format json | grep` to filter for specific methods.

## Docker

`Dockerfile` packages the Node.js entry. It must be built from the **repository root** (`docker build -f mcp-app-server/Dockerfile -t drawio-mcp-app .`) because `src/index.js` reads `../../shared/*.md` and `../../shape-search/search-index.json` at startup and `src/shared.js` imports `../../shared/*.js` — a build context of just this directory cannot see them. The root `.dockerignore` trims the context to what the `COPY` lines need (no `node_modules`, `.git`, `public/`, or the other packages). `wrangler` is a devDependency and is left out of the image (`npm ci --omit=dev`). The Node entry binds to `LISTEN` (default `127.0.0.1`); the image sets `LISTEN=0.0.0.0` so `-p` works, and the docs recommend `-p 127.0.0.1:3001:3001`. `ALLOWED_HOSTS` turns on the SDK's Host header check — deliberately not implied by a loopback bind, since tunnels (cloudflared, Tailscale Funnel) connect to localhost but forward their public Host.

**Publishing to Docker Hub** — `.github/workflows/publish-app-server-image.yml` (manual `workflow_dispatch`, like the tool server's npm publish) builds the Dockerfile for `linux/amd64` + `linux/arm64`, smoke-tests the native build first (`initialize` must answer as `drawio-mcp-app` and the `io.modelcontextprotocol.server.name=io.draw/mcp` label must be present — the label the MCP registry requires before an OCI package can be listed in `server.json`), then pushes `jgraph/drawio-mcp:<version>` and `:latest`, where `<version>` is this `package.json`'s — bump and commit it first; a tag that already exists on Docker Hub fails the run before anything is built. It also syncs `DOCKER_HUB.md` to the Hub page (that step needs a token with Read, Write and Delete scope and is `continue-on-error`). Needs the `DOCKERHUB_USER` / `DOCKERHUB_TOKEN` repository secrets (the same names as jgraph/docker-drawio). Run with `gh workflow run publish-app-server-image.yml`; `-f dry_run=true` builds and smoke-tests without logging in or pushing.
