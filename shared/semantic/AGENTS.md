# Semantic diagrams

The model describes what a diagram contains (nodes, groups, edges, see `FORMAT.md`), never coordinates, sizes or styles, at most a row and a column per node; this engine turns the description into draw.io XML. Placing every shape itself is where a model spends most of its time on a diagram: in the bench (`bench/`), Sonnet took about 50 s to an ER diagram as XML and about 6 s as a description, Opus 228 s and 12 s, and the engine takes 15 to 70 ms.

The app server has it as a tool of its own, `create_semantic_diagram`, next to `create_diagram` rather than as a third parameter of it (its description, within the 2048 characters, lists only the types offered; see `mcp-app-server/AGENTS.md`). The tool is listed only for the types switched on in `SEMANTIC_TYPES_ON` (`mcp-app-server/src/shared.js`), and none is by default, so nothing is offered to models and `tools/list` is unchanged. Flowcharts and swimlanes passed the judgement and are behind a switch until the staging test: `DRAWIO_SEMANTIC_TYPES=on` offers them (`SEMANTIC_TYPES_READY`), in the Node server at startup and in the Worker at build time; a list such as `er` offers other types for trying them out. `bench/semantic-server.mjs` offers the tool for the measurements, with the types, the kind of placement hints and the wording of the description set per run. A type is switched on only once a blind judgement of the rendered images rates its layouts at least equal to the model placing the XML itself (`bench/README.md`).

## Rules

- **Headless and deterministic.** No DOM, no `fetch`, no timers, no randomness: the same description gives the same XML byte for byte, in the Cloudflare Worker, in Node (both servers, the skill's scripts) and in the browser. Text is measured with Helvetica's widths (`text-width.js`), which is what the viewer falls back to.
- **Own code or public packages.** Everything here is written for this engine or comes from a public npm package. What the layouts need beyond that (a lane layout, text measurement with line wrapping, icons by name, scoring layouts) is written here too. ELK is optional and passed in (`options.elk`, `new ELK()` from elkjs or the browser's global), never imported, so each host brings its own copy. The Cloudflare Worker passes none for now (no elkjs in its bundle), so there ER schemas above 16 tables go on the grid as well, with its search limited (see ER layout).
- **The look of `shared/chat-view-xml.md`.** Each layout follows the pattern that file asks models for, in the calm theme (`theme.js`, the colors of the "Calm" theme in `shared/xml-reference.md`), so a diagram drawn from a description and one the model places look the same. When a pattern changes there, change it here too.
- **Leniency with warnings.** `spec.js` reads what models get wrong (a JSON string, for the description or a list in it, `source`/`target`, any case, type aliases such as `erd`, field lists as one string) and drops what can't be drawn with a warning instead of failing the call. The app server's tool schema reads the type and the lists with the same functions (`typeName`, `readList`), so the server never rejects what the viewer's preview has already drawn. A list whose JSON text is still streaming in counts as empty, not as one item named after the text.
- **XML stays the way out.** The engine's output is plain draw.io XML that goes through the server's usual passes (repair, normalization, waypoint snapping, label perimeters) without them finding anything to change; ids follow the description (`table.field` for rows, `child-parent` for relations). Tables are written as the table shorthand of `shared/diagram-shorthand.js` (a `rows` attribute, the role's colors from `theme.js`, whose role list is longer than the shorthand's) and expanded before `semanticToXml` returns, so a table drawn from a description and one a model writes as XML are built by the same code; no `rows` is left in the result.
- **Module syntax the viewer can bundle.** The app server's viewer runs the engine while a description streams in, as one classic script built by `mcp-app-server/src/semantic-bundle.js`. That bundler reads only single-line named imports of relative paths (`import { a, b as c } from "./x.js";`), `export` in front of a function, class, `const`, `let` or `var`, and `export { a, b };`; anything else fails its test (`semantic-tool.test.js`) rather than the viewer.

## ER layout

Up to 16 tables go on a grid of two to four columns (`gridGeometry` in `er.js`). Each column count is placed (`placeOnGrid` with `linkCost`: a link between neighbouring columns in one row costs nothing and 0.8 per row apart, one in the same column needs a C-shaped route, one across a column costs most) and routed (`routeGrid`), and the result with the lowest badness is kept: link cost, crossings ×4, collinear overlaps ×4, bends ×0.15, the lines' length per 250 px, crowded ends ×1.5 (`crowdedOf`: more than one relation ending on the same side of a table at the same height) and how much the diagram would have to shrink to fit the 800 × 800 chat frame ×40. The refinement on routed results starts from every start for up to 10 tables (`REFINE_ALL_MAX`) and from the best one above, which keeps 16 tables under half a second. Every swap search stops at a work limit (`LINK_WORK`, `ROUTE_WORK` in `grid.js`: the swaps tried, weighted by the links or the pairs of links one costs) and keeps the best placement found so far; up to 16 tables with the usual number of relations it isn't reached and the layout is unchanged, above, a schema without ELK stays around a second (60 tables 0.9 s, 200 tables 1.4 s, where 24 tables took 6 s and 60 more than a minute before), so a large description can't hold up the server or the viewer's preview. Tables linked to a neighbour in the same grid row are shifted down (`alignRows`, at most three rows' height) so the rows they connect line up and the line between them is straight. A relation between two tables of one column runs in a gutter beside them, inside the grid or outside its edge column (`grid.outer`); both are routed and the better kept. A relation whose rows are within half a row of each other is drawn straight. Relations that end on the same row (several tables referencing one key) get their own points on it, 10 px apart and ordered by where they come from, so no two share a stub or a track. Larger schemas use ELK's layered algorithm (`elkGeometry`) with fixed ports at the row centres when an ELK instance is passed in, and the grid otherwise. The search by link costs sums only the two swapped boxes' links for each swap (`improveByLinks`), with the same result as summing all of them.

How the layouts compare with the XML models place themselves is measured with `bench/` (blind judgement of the rendered images). What the judge asked for so far: related tables side by side in one row, few crossings, short lines, and no relations sharing a line. A first version laid every schema out with ELK's layered algorithm (one tall column of layers, the relations bundled in narrow gaps) and lost every comparison; the grid, the separate points per relation and the weights above came from those judgements. In November 2026 the grid tied with the schemas Sonnet placed as XML (9 of 18 judgements on three prompts, mean score 6.9 against 6.6) and still lost to the one Opus placed (2 of 2). With the alignment, the outer gutters, the crowded ends and the heavier crossings it tied with both: 9 of 18 for Sonnet's (mean 7.0 against 6.8) and 1 of 2 for Opus's, the layout check finding nothing in any of them. By prompt it isn't there yet: the shop schema won 6 of 6, the library 1 of 6 (a relation crossing another, two relations crowding one key) and the clinic 2 of 6 (the owners table in the middle, read out of order).

## Architecture, network, flowchart and swimlane: one grid pass

These four types have no layout module of their own. `boxes.js` writes what a model could write itself, compact XML without any geometry, and `shared/grid-layout.js` places it: a pass over the draw.io model like the normalization (`gridLayoutDiagram(xml, {mode, direction, hints, frame})`, geometry-less cells in, geometry and routed edges out). So the XML path can use the same pass for a diagram whose cells have no positions, and whatever the pass learns, both get. It only touches pages with a vertex that has no position, unless `all` is set.

- **Sizes** come from the text (`text-width.js`, with line wrapping): boxes of one kind share the size of the fullest one, icons are 60 px with their label below (in the diagram's text color, since some icon sets bring a grey of their own), and a decision is as narrow as its question allows on two or three lines (160 to 240 wide, 90 high or more; `DECISION_FILL`, and `DECISION_WRAP` in `boxes.js`), since a row of decisions 240 wide made a large flowchart half again as wide as the one a model places.
- **With hints** (`row=`, `col=` in a cell's style, removed by the pass): the model's cells, on a grid with a column as wide as its widest cell and a gap as wide as the label of a line that runs straight through it needs. Read per container by default: every container has its own grid, and frames alone in their cells get one height per row and one width per column.
- **One grid for the page** (`hints: "page"`, what `semanticToXml` passes for `hints: "ask"`): every shape names its cell in one grid for the whole page, as a model does when it writes coordinates (`placeOnPage`). Columns and rows are as large as their fullest cell and hold across the frames; a frame is drawn around the cells of its members, with room in the gaps for its border and title and for those of the frames nested in it. A shape in the block of a container it isn't in moves out by the shortest way (`moveStrangers`). Lanes are bands of that grid, rows or columns each lane has to itself, and the pass turns them the other way when the chat then shows clearly more of the diagram (`TURN_MARGIN`) and shows it whole. Cells that can't be drawn so (a shape without one, lanes that share rows and columns) fall back to a grid per container, each frame taking the first cell of its members.
- **Without hints, tiers** (`mode: "tiers"`, architecture): ranks by the connections, the order in a rank by the barycenter of its neighbours, every rank centered and moved towards what it connects to. A run of ranks without frames beside a rank with one is folded into one rank; a level without frames that is longer than the chat frame continues beside itself.
- **Without hints, flow** (`mode: "flow"`, flowcharts): the main path in one line, branches beside the step they leave, a snake when the path is longer than the frame. Lanes (`lane=1`) share one grid and become columns or rows.
- **Direction**: every nesting level can run down or to the right. The page is placed once per policy (each level for itself, all down, all right, alternating either way) and the one of which the chat shows most wins, shorter connections second. A level can't decide that for itself: it doesn't know how much of the frame the levels around it leave.
- **What the chat shows** (`shown`): the frame is 736 × 664 px (`FRAME`: the viewer's card in an 800 px chat on a screen 1000 px high, less its padding, measured on the bench's screenshots). A diagram is shown whole down to a scale of 0.75; below that the viewer shows the top of a tall one at the scale of its width and cuts the rest off, which the score counts as the scale times the square of the visible share. A page that doesn't fit at full size is placed again with less room between its cells and inside its frames (`SPACING.tight`), and then with narrower boxes as well (140 instead of 160 at 16 px), which it keeps when the page is then shown larger by `DENSE_MARGIN`.
- **Lines on the page's grid** (`shared/grid-lines.js`): a model that writes coordinates leaves room for its lines, one that names cells can't, so the pass does it. The lines are planned on the grid before its sizes are final (`planLines`): each one is a shortest path through the gaps between the columns and rows, the free cells and the rim around the grid, with costs for bends, crossings, running through a frame that is neither end's, crossing a frame's title and a side of a shape that is taken (short lines first, then two rounds in which every line is routed again knowing the others). Every straight piece then gets a track of its own in its gap, in the order with the fewest crossings, and the grid is placed again with the room the tracks need: in every gap, around the grid, and inside a frame's border for the lines between its own members, which stay in the frame. On the final sizes (`drawLines`) every line gets its own point on the side of its shape, what can be straight is straightened, pieces that would run on each other are moved apart, and every label goes on the piece of its line where it touches least, the outcome of a decision beside the decision. A frame's title moves aside (`align=left;spacingLeft`) when a line comes in where it stands, since the viewer reroutes a diagram whose line crosses a title. A line that ends at a frame ends at its border, 30 px from the shapes inside (`FRAME_END`), and a labeled one from the shape beside the frame gets the room for its label before the border; right beside a member it read as a line to that member. A labeled line that runs down past a row has its label between the rows and needs no wider gap. `route: false` writes no routes and keeps the room, for the viewer's router.
- **Trees** (`bundle=<n>` in an edge's style, removed by the pass): the lines of one bundle are planned as one tree. They may share pieces (`SHARED_PX`), leave their common end at one place per side, and don't count as crossing each other; everything else still keeps its own track.
- **Shown whole**: a page that the chat would cut off at the bottom is made wider until the viewer shows it whole (`canWiden`, down to a scale of `WHOLE_FROM`, 0.3: the frame has the room beside a tall diagram), and it is scored with that scale; the notes under the diagram count as part of its height. The limit was 0.5 until three large dev diagrams between 0.42 and 0.46 were judged both ways: whole they scored 7 to 8, cut off 3 to 4, because what is cut off counts as missing. A page without lanes is turned (rows as columns) only when the chat then shows a fifth more (`TURN_MARGIN_PAGE`); a flowchart without lanes for any gain worth having (`TURN_MARGIN_FLOW`, 0.03), since its rows and columns mean nothing but the order. A turned page is widened at any scale.
- **A group as an end** (`bundleEdges` in `boxes.js`, architecture and network): an edge between a node and a group means every member. Where the 2 to 8 members stand in one row or column of the grid and the node in the next one that holds anything (`isComb`), it becomes one line per member in one bundle, with the label once; at most two such connections per group, and not the same connection with several groups (logs from everything), which is about the groups. The page is placed with these trees and with one line to the frame instead, and the trees stay unless they cost more than one crossing more (`FAN_CROSSINGS`): two hubs on the same side of one column of services cross each other's branches. Three or more edges written one by one that share an end, a kind and a label are a bundle too. An edge between a group and something inside it has no line: `splitNotes` writes it as a line of text under the diagram (`id="notes"`, `note=1` for the pass, which places such text below the diagram and the heading above).
- **Edges elsewhere** (a grid per group, tiers, flow): for every right-angle edge a handful of candidate routes (straight, one bend, two bends, around the outside) is scored by bends, length, shapes in the way, crossings with routes already chosen and the sides already in use; the winner is written as exit and entry points and waypoints.

## A change keeps the layout

A change is the whole changed description, laid out again. Without more, the pass decides everything anew (the orientation, the spacing, the font size by the number of shapes, the sizes of the boxes, how much a tall page is widened), and in the first measurement three quarters of the shapes moved. So the result of a description with one grid for the page (`hints: "ask"`) has a `layout` (`keep.js`), and a change that passes it back is placed around what was there. The server keeps no diagrams, so the earlier layout has to travel with the call: the text holds all of it, 40 to 150 characters.

- **What is kept** (`options.keep` of `layoutPage`): the policy (turned or not) and the spacing (tight, narrow boxes) without searching them again; the font size of the shapes (`compactXml`'s `font`, `fontSizesOf` in `theme.js`), also when the change crosses the 12 shapes where it would change; the size of every kind of box (`unifySizes` with the earlier sizes as the least: the same names, shape and corners), so a box only grows when its own text needs it; and every column and row by the number the model gave it (`keptAxis` in `placeOnPage`): it keeps at least its size and its center, unless what comes before it needs more room. Nothing shrinks. A number that is new gets the room it needs and moves only what comes after it; a number that is gone leaves its place empty.
- **Widening:** a page that the change made tall enough to be cut off is made wider, as a page laid out anew is, but around its columns instead of across them (`ctx.keepWidth`), so the chat still shows it whole and no step moves against another. A lane diagram is widened at its right end, where the lanes reach. On any other page the columns move together, with the gaps beside them, to the middle of the wider page; the chat fits the diagram again, so the shift they share doesn't show, and the layout of the result is written without it. A turned page is widened at any scale, as a fresh one. The viewer fits the shapes, not the page, so on a page without lanes the wider page shows through the title above it, which spans the page up to 600 px, as when a fresh single-column page is widened. Until the review of PR 109 only lane diagrams were widened on a change, which is what the eighth measurement ran with.
- **What still moves:** what the model renumbers (a step put in between, with the columns after it one further, moves those steps by one column, as it would on paper), and what makes room for something new: a column that a wider box joins grows on both sides of its center, a gap that a new line needs a track in grows by about 10 px, and the rows or columns after them follow.
- **Guarded:** a layout is used only for a description with the same type and title and when it was copied exactly (the checksum); otherwise the diagram is laid out anew, with a warning that says why. The numbers are rounded down, so the same description with its own layout is drawn exactly as before, also after many changes.
- **The tool:** `create_semantic_diagram` returns the layout in its payload and in a second text block that says how to change the diagram with it (`semanticChangeNote`), the description and the schema ask for it (`layout`, before `nodes`, so the viewer's preview of a change draws the shapes where they were from the start), and the viewer's update for the model repeats it (`modelContextText`).
- **What it costs** (the eighth measurement): the same changed description laid out anew is preferred a little more often than with the layout kept (mostly ties; the kept one loses a third), because a kept page that grows wider is shown smaller, a taller lane diagram gets its width in the last lane, and new lines go around steps that stayed. Stability is the rule here: nothing falls back to a fresh layout when keeping looks worse.

What the measurements in `bench/` say so far (November 2026, Sonnet and Opus, 12 held-out prompts, three runs each) is in **Results** below. In short: the description is 3 to 8 times faster to write than placed XML, the layouts the pass finds on its own lose against the ones a model places by hand, and the ones where the model names the cells of one grid for the page, with the lines planned and given room, win half of the comparisons on the held-out prompts (Sonnet 0.54, Opus 0.50). Flowcharts and swimlanes pass the gate for both models (0.75 and 0.78, no prompt below 0.33) and are offered behind the app server's switch (`DRAWIO_SEMANTIC_TYPES=on`) until the staging test. Architecture, cloud and network don't (0.33 and 0.22): the two large diagrams of about 35 shapes have won 3 of 120 judgements over the five wordings of the fifth measurement, so a tool that has `create_diagram` beside it takes these types only up to 18 nodes (`MAX_NODES`), and they stay off. Of the three parts of the tool description's later wording, measured one by one, only the placement rule is kept (the fifth measurement). The viewer's preview keeps the way round it has shown a diagram, so none turns more than once while it grows, and flowcharts without lanes of more than 24 nodes go to `create_diagram` as XML (`MAX_NODES_WITHOUT_LANES`). The size rule names no number to the model, since a model that knew it wrote its descriptions to it, and the gate leaves out the pairs that the rule sends to `create_diagram`, since they don't measure the semantic tool. Read that way, on its own three runs with the server's own tool, Sonnet passes with 0.87 and Opus with 0.70, no prompt below 0.33 (the sixth and seventh measurements). A change that passes the first result's layout back keeps the nodes it doesn't touch in place: of those, Opus's moved 26 of 167 instead of 116 of 178, Sonnet's 60 of 186 where it passed the layout, at a small cost in the judgement of the changed diagram (the eighth measurement).
