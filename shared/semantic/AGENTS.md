# Semantic diagrams

The model describes what a diagram contains (nodes, groups, edges, a direction, see `FORMAT.md`) and never where anything goes or how it looks; this engine turns the description into draw.io XML. Placing every shape itself is where a model spends most of its time on a diagram: in the bench (`bench/`), Sonnet took about 50 s to an ER diagram as XML and about 6 s as a description, Opus 228 s and 12 s, and the engine takes 15 to 70 ms.

The app server has it as a tool of its own, `create_semantic_diagram`, next to `create_diagram` rather than as a third parameter of it (its description, within the 2048 characters, lists only the types offered; see `mcp-app-server/AGENTS.md`). The tool is listed only for the types switched on in `SEMANTIC_TYPES_ON` (`mcp-app-server/src/shared.js`), and none is yet, so nothing is offered to models and `tools/list` is unchanged; `DRAWIO_SEMANTIC_TYPES=er` offers ER schemas in the Node server for trying it out. `bench/semantic-server.mjs` offers it for the measurements. A type is switched on only once a blind judgement of the rendered images rates its layouts at least equal to the model placing the XML itself (`bench/README.md`).

## Rules

- **Headless and deterministic.** No DOM, no `fetch`, no timers, no randomness: the same description gives the same XML byte for byte, in the Cloudflare Worker, in Node (both servers, the skill's scripts) and in the browser. Text is measured with Helvetica's widths (`text-width.js`), which is what the viewer falls back to.
- **Own code or public packages.** Everything here is written for this engine or comes from a public npm package. What the layouts need beyond that (a lane layout, text measurement with line wrapping, icons by name, scoring layouts) is written here too. ELK is optional and passed in (`options.elk`, `new ELK()` from elkjs or the browser's global), never imported, so each host brings its own copy. The Cloudflare Worker passes none for now (no elkjs in its bundle), so there ER schemas above 16 tables go on the grid as well, with its search limited (see ER layout).
- **The look of `shared/chat-view-xml.md`.** Each layout follows the pattern that file asks models for, in the calm theme (`theme.js`, the colors of the "Calm" theme in `shared/xml-reference.md`), so a diagram drawn from a description and one the model places look the same. When a pattern changes there, change it here too.
- **Leniency with warnings.** `spec.js` reads what models get wrong (a JSON string, for the description or a list in it, `source`/`target`, any case, type aliases such as `erd`, field lists as one string) and drops what can't be drawn with a warning instead of failing the call. The app server's tool schema reads the type and the lists with the same functions (`typeName`, `readList`), so the server never rejects what the viewer's preview has already drawn. A list whose JSON text is still streaming in counts as empty, not as one item named after the text.
- **XML stays the way out.** The engine's output is plain draw.io XML that goes through the server's usual passes (repair, normalization, waypoint snapping, label perimeters) without them finding anything to change; ids follow the description (`table.field` for rows, `child-parent` for relations). Tables are written as the table shorthand of `shared/diagram-shorthand.js` (a `rows` attribute, the role's colors from `theme.js`, whose role list is longer than the shorthand's) and expanded before `semanticToXml` returns, so a table drawn from a description and one a model writes as XML are built by the same code; no `rows` is left in the result.
- **Module syntax the viewer can bundle.** The app server's viewer runs the engine while a description streams in, as one classic script built by `mcp-app-server/src/semantic-bundle.js`. That bundler reads only single-line named imports of relative paths (`import { a, b as c } from "./x.js";`), `export` in front of a function, class, `const`, `let` or `var`, and `export { a, b };`; anything else fails its test (`semantic-tool.test.js`) rather than the viewer.

## Files

| File | Purpose |
|------|---------|
| `index.js` | `semanticToXml(input, {elk})` → `{xml, error, warnings, stats}` (the shorthand expanded), and `SUPPORTED_TYPES` (the types with a layout) |
| `spec.js` | `normalizeSpec`: reads a description into one shape (`TYPES`, aliases, warnings); `typeName` and `readList`, which the app server's tool schema uses too |
| `description.js` | `describeTool(types)`: the tool description for the switched-on types (each server caps descriptions at 2048 characters) |
| `er.js` | ER schemas: fields (`parseField`), relations from foreign-key rows to primary-key rows (`resolveRelations`), table sizes, grid or ELK layout, the cells |
| `grid.js` | Grid placement (`placeOnGrid`: link costs, swaps from three deterministic starts, an optional refinement on routed results, each search within a work limit) and channel routing (`routeGrid`: one track per link in the gutters between columns and the gaps between rows, track order searched for the fewest crossings; `alignRows` shifts linked boxes of one row so their lines run straight) |
| `theme.js` | Calm colors by role, edge colors, font sizes by shape count |
| `text-width.js` | Helvetica advance widths for headless text measurement |
| `xml-writer.js` | Escaping, html labels, unique ids, `writeModel(cells)` |
| `FORMAT.md` | The format, for every planned type |

## ER layout

Up to 16 tables go on a grid of two to four columns (`gridGeometry` in `er.js`). Each column count is placed (`placeOnGrid` with `linkCost`: a link between neighbouring columns in one row costs nothing and 0.8 per row apart, one in the same column needs a C-shaped route, one across a column costs most) and routed (`routeGrid`), and the result with the lowest badness is kept: link cost, crossings ×4, collinear overlaps ×4, bends ×0.15, the lines' length per 250 px, crowded ends ×1.5 (`crowdedOf`: more than one relation ending on the same side of a table at the same height) and how much the diagram would have to shrink to fit the 800 × 800 chat frame ×40. The refinement on routed results starts from every start for up to 10 tables (`REFINE_ALL_MAX`) and from the best one above, which keeps 16 tables under half a second. Every swap search stops at a work limit (`LINK_WORK`, `ROUTE_WORK` in `grid.js`: the swaps tried, weighted by the links or the pairs of links one costs) and keeps the best placement found so far; up to 16 tables with the usual number of relations it isn't reached and the layout is unchanged, above, a schema without ELK stays around a second (60 tables 0.9 s, 200 tables 1.4 s, where 24 tables took 6 s and 60 more than a minute before), so a large description can't hold up the server or the viewer's preview. Tables linked to a neighbour in the same grid row are shifted down (`alignRows`, at most three rows' height) so the rows they connect line up and the line between them is straight. A relation between two tables of one column runs in a gutter beside them, inside the grid or outside its edge column (`grid.outer`); both are routed and the better kept. A relation whose rows are within half a row of each other is drawn straight. Relations that end on the same row (several tables referencing one key) get their own points on it, 10 px apart and ordered by where they come from, so no two share a stub or a track. Larger schemas use ELK's layered algorithm (`elkGeometry`) with fixed ports at the row centres when an ELK instance is passed in, and the grid otherwise.

How the layouts compare with the XML models place themselves is measured with `bench/` (blind judgement of the rendered images). What the judge asked for so far: related tables side by side in one row, few crossings, short lines, and no relations sharing a line. A first version laid every schema out with ELK's layered algorithm (one tall column of layers, the relations bundled in narrow gaps) and lost every comparison; the grid, the separate points per relation and the weights above came from those judgements. In November 2026 the grid tied with the schemas Sonnet placed as XML (9 of 18 judgements on three prompts, mean score 6.9 against 6.6) and still lost to the one Opus placed (2 of 2). With the alignment, the outer gutters, the crowded ends and the heavier crossings it tied with both: 9 of 18 for Sonnet's (mean 7.0 against 6.8) and 1 of 2 for Opus's, the layout check finding nothing in any of them. By prompt it isn't there yet: the shop schema won 6 of 6, the library 1 of 6 (a relation crossing another, two relations crowding one key) and the clinic 2 of 6 (the owners table in the middle, read out of order).

## Tests

`mcp-app-server/test/semantic-er.test.js` (`npm test` there): reading fields and multiplicities, lists as JSON text (also cut off while streaming), every role's colors, the rows a relation connects (two references to one table, a reference to its own table), leniency and warnings, determinism, the server's passes finding nothing to change, tables as the shorthand expands them, no crossings or overlaps for a chain and a star, a straight line between tables side by side, the description length, a 60-table schema without ELK in bounded time, and the ELK path when `elkjs` can be resolved (`NODE_PATH`, or `bench/node_modules`). `mcp-app-server/test/semantic-tool.test.js`: the tool, listed only with a type switched on, its answer and its leniency (aliases, `null`, nodes by id alone), and the bundle for the viewer giving the same XML as the modules.
